# Contributing

## How this repository is maintained

The kit is developed in a private development repository at Impact AI. Each release comes here as **one commit**,
`Release X.Y.Z`, that replaces the whole tree with the tree of the development commit it was made from, in a pull
request of its own: CI runs on it here, a maintainer reviews and merges it, and the tag `vX.Y.Z` on the merged commit
starts the release workflow, which builds, tests, signs and publishes the release. The history of development, its
branches and its pull requests stay in the development repository, and dependency updates are made there.

* **Issues are welcome here**: bugs, documentation errors and feature requests ([SUPPORT.md](SUPPORT.md)).
  Vulnerabilities go to [SECURITY.md](SECURITY.md), never to an issue.
* **Pull requests are welcome too.** Open an issue first for anything larger than a fix, so that we can agree on the
  approach. A pull request is reviewed here; once it is accepted it is carried into the development repository, with
  you as its author, and lands in the next release. It is not merged here: a commit merged here directly would be
  replaced by the next release.
* **Sign off your commits** ([Developer Certificate of Origin](https://developercertificate.org/)): `git commit -s`
  adds `Signed-off-by: Your Name <you@example.com>`, which certifies that you wrote the change or have the right to
  submit it under the project's license, Apache-2.0. A check on each pull request looks for it on every commit.
* Follow the [code of conduct](CODE_OF_CONDUCT.md).

## Design rules

Everything here runs in a customer's production cluster. A change keeps to these rules, and the tests hold most of them.

* **Never break the customer's application.** Injection fails open (webhook `failurePolicy: Ignore`, a short timeout,
  system namespaces excluded). The instrumentation stands down when the process already has another tracer.
* **Names, never values.** The reporter sends names only: no environment values, container arguments, ConfigMap or
  Secret contents, and only allowlisted annotations. Its RBAC never includes Secrets or ConfigMaps.
* **No privileged pods.** Images run as non-root where the Operator allows it.
* **Supply chain.** Base images are pinned by digest, Python packages by hash and npm packages by the integrity hash of
  their lock file (installed with `--ignore-scripts`: no package code runs in a build); images are built with
  provenance and SBOM; no credentials in images. The Java image takes no build tool (no Maven or Gradle, no dependency
  resolution): every jar is fetched from Maven Central by URL and SHA-256 (`ADD --checksum` in `java/Dockerfile`), and
  the upstream agent goes into the image unchanged, nested in the kit's launcher. A test fixture keeps a version with a
  known vulnerability only when that version is what it tests (a library's oldest traced series, what a vendor's
  distribution installs): `testing/apps/osv-scanner.toml` names it with its reason, and the dependency review allows
  the same id (`.github/dependency-review-config.yml`; a test keeps the two the same).
* **Node.js preload.** `nodejs/src` loads on Node 16 too and never throws: every failure is caught and reported in the
  `impact.setup` span. ES modules are traced only where `nodejs/qualification.json` proves it, because the loader hook
  can break a library that was not tested (openai 4's ES module build). The image carries no provider SDK; its package
  called `openai` is a stand-in (`nodejs/shims/openai`).
* **Python libraries.** An AI library is traced only where the passing cells of `python/qualification.json` for the
  workload's Python prove its version. A library joins the traced set in the change that adds its passing cells.
* **Overhead.** An injected workload costs at most +1.5 ms of CPU per model call, +40 MiB and +2 s to start. Do not
  raise a budget to pass: find the cost.
* **Contracts with the Impact AI service.** The inventory format and the `impact.setup` span are a contract with the
  service; the service changes first, then this repository's code and tests.
* **No detection, scoring or guard logic here.** Verdicts are computed by the Impact AI service; the kit collects and
  sends.
* **Public and Apache-2.0.** Every source file of ours starts with `SPDX-License-Identifier: Apache-2.0`
  (`make licenses` adds it), and nothing internal reaches the repository, the chart or the images: internal hosts,
  e-mail addresses, account IDs, private addresses, tokens, planning ids and the names of private repositories.
  `make lint` and `make release` check both with `scripts/check_internal_details.py`; a fixture value is allowed only by
  name, with a reason, in that script. The licenses of what the images bundle are generated by the build, never written
  by hand.

## Build and test

Everything CI runs is a `make` target; `make help` lists them. The tools and their versions are in `mise.toml`
(`mise install`, trivy included), and the image and container tests need a container engine (`CONTAINER=docker`, or
`podman`).

| Target | What it runs |
|---|---|
| `make lint` | ruff, gofmt and go vet, `helm lint`, the vendored Operator chart against its pin, trivy on the rendered chart, SPDX headers, nothing internal in the source or the rendered chart |
| `make test-python`, `make test-reporter`, `make test-chart` | unit tests of the Python package and payload, the reporter's tests with the race detector, the chart's render checks |
| `make ci` | lint, unit tests, chart checks, image builds, the trivy scan of the images, the container tests that reproduce the Operator's injection, and an overhead canary |
| `make e2e` | the kind end-to-end suite, then the tracer, agent framework, Node.js matrix and AI gateway container tests and the Python qualification cells a change touches (about 25 minutes) |
| `make overhead` | the overhead of every runtime and server against the budget; needs the machine to itself |
| `make ci-jobs` | which CI jobs a change needs, and why (`scripts/ci_jobs.py`) |

**`make ci`** in detail: lint (style, license headers, nothing internal in the source or the rendered chart), unit tests
(the Node.js package's run in a container, `make test-nodejs-unit`), chart checks, image builds, the trivy scan of the
released images, and the container tests that reproduce the Operator's injection:

* Python 3.11 to 3.14 under uvicorn and gunicorn, a Starlette and Bedrock Nova workload, a library version the
  qualification does not prove (`make test-image`);
* Node.js 22, 24 and 26 (`make test-nodejs`): layout, a preload that never throws on Node 16 to 26, one span with
  content per model call, stand-down beside another tracer, ingest down, ES modules where the qualification proves them;
* the Java image (`make test-java`);
* the gateway's Collector forwarding spans and log events with the cluster's placement
  (`python/tests/image/test_kit_gateway_logs.py`);
* an overhead canary (`make overhead-canary`).

**`make e2e`**: the kind end-to-end suite, then the container tests that need the largest fixtures: those of the
tracers, of the agent frameworks (OpenAI Agents SDK, LangChain, LangGraph; `make test-agents` alone, on the Pythons of
`AGENTS_PYTHONS`, default "3.12 3.13 3.14"), the Node.js qualification matrix (`make test-nodejs-matrix`: Node 22, 24 and
26 as CommonJS and as ES modules against OpenAI's SDK 4 to 7 and Anthropic's from 0.134), the AI gateways (a LiteLLM
proxy and a Portkey gateway, by digest, against the mock) and the cells of the Python qualification of the libraries
the change touches (`make test-python-cells`). `E2E_NODE_IMAGE=<kindest/node image>` runs the Kubernetes part on
another version.

On a workstation, kind runs a whole cluster inside the user's own process limits, and the Linux default of 128 inotify
instances per user (`fs.inotify.max_user_instances`) is easily used up by a desktop plus a cluster; the Operator then
crash-loops with "couldn't initialize inotify: too many open files". `scripts/e2e.sh` raises the limit with `sudo -n`
when it may (CI can); elsewhere run `sudo sysctl -w fs.inotify.max_user_instances=1024` once.

**How CI runs them.** Each job finishes in under ten minutes. The parts of `make ci` run for every pull request, a draft
too, and every push to main. The parts of `make e2e`, on Kubernetes 1.34 and 1.27, run once a day on main when it
changed in a way they can see (with `make overhead`), and on every release before anything is published. A pull request
labelled `run-full-ci` runs the suite as well, one labelled `benchmark` the overhead. The jobs and their time limits are
in `.github/workflows/ci.yml`; `make ci-jobs` says what an event runs.

**Overhead.** `make overhead` measures what an injected workload costs more than the same workload without injection,
for every runtime and server the images claim, each calling OpenAI, and for a library that joined the traced set with
cells of its own a workload that calls it: three paired rounds each, the median of the differences held to the
budget, a failing workload measured once more ([compatibility](docs/compatibility.md#overhead) has the method and the
Node.js memory reading). `make release` runs it before anything is pushed and publishes the numbers in the chart.

## The qualifications

* **Node.js.** `make qualify` runs the Node.js matrix again and rewrites `nodejs/qualification.json`: the preload traces
  an ES module application only where that file proves it, and `make test-nodejs-matrix` fails when a cell no longer
  says what it did. A workload can override the file with `IMPACT_NODEJS_ESM=on` (try an ES module anyway) or `off`.
* **Python.** `python/qualification.json` has a cell per Python version (3.11 to 3.14), AI library and major version
  of it (OpenAI, Anthropic, Bedrock through botocore, the OpenAI Agents SDK, LangChain, `langchain-core`, LangGraph and
  Google's `google-genai`). Each says whether a workload with it started and served, whether its model calls arrived as spans with
  provider, model and tokens, where their content arrived and, for an agent framework, whether its agent and tool steps
  arrived. The package traces a library only where the cells of the workload's Python prove its version: from the
  oldest passing cell of that library to the newest (each library has a cell at the oldest series the image traced
  before the qualification, in the fixture `oldest`, and one at its newest), broken where a cell between them fails.
  `scripts/qualify_python.py` names the cells.
  * `make test-python-cells` runs the cells a change touches: none for most changes; a library's cells on every Python
    for a change to that library's fixture, package or cells; every library on Python 3.12 for a change to the package.
    The end-to-end job runs it.
  * `make test-python-matrix` runs every cell and fails when one no longer says what it did. `make release` runs it
    before anything is pushed.
  * `make qualify-python` runs them again and rewrites the file.
  * `make test-python-newest` runs each library's newest series on its newest release and fails when one fails its cell
    (a release that fails is listed under `excluded` in the next kit release) or passes in a series no cell proves (it
    is not traced until `make qualify-python` adds its cell, so the run asks for it).

## Releases

A release starts with the tag `vX.Y.Z` in this repository; the release workflow runs `make release`:

1. Before anything is pushed: nothing internal in the source and the chart; every image built for `linux/amd64` and
   `linux/arm64` and scanned (a fixable CRITICAL or HIGH vulnerability, or an internal detail in its files, stops the
   release); the overhead of every runtime and server within the budget; every cell of the Python qualification as the
   file says; and `SECURITY.md` without a placeholder.
2. It publishes the images `autoinstrumentation-python`, `autoinstrumentation-nodejs` and `kubernetes-reporter`, with
   provenance and SBOM, to `ghcr.io/impact-ai/<image>`, and the chart to `oci://ghcr.io/impact-ai/charts/impact-ai`
   with the images' digests written into it. They go to the root of the organisation: the registry host and the
   lowercased owner of the repository the release runs in (`PUBLISH_ROOT` replaces it; `scripts/names.sh`).
   `autoinstrumentation-java` is published only when the workflow sets `RELEASE_JAVA=1`, which it does in the same
   change that records that image's provenance; the workflow does not set it yet.
3. After the push the chart and the images are signed by digest with cosign (keyless: the workflow's own identity, no
   key to keep), each image gets a signed SPDX bill of materials, and GitHub records the build provenance of the chart
   and each image. `make verify-release VERSION=vX.Y.Z` checks a published release the way a customer does; the
   commands are in the chart README under "Verify what you install".

A release is made in this repository only: `make release` refuses to run anywhere else unless `RELEASE_REHEARSAL=1` says
that it is a rehearsal against a registry of your own. Before the release, the end-to-end suite runs on the tagged
commit.

## Updating the vendored Operator chart

`python3 scripts/vendor_operator_chart.py` rebuilds `chart/impact-ai/charts/opentelemetry-operator/` and
`chart/impact-ai/crds/` from the pinned upstream release (SHA-256 verified); `--check` fails when they differ. The only
changes to upstream are a guard on every object template (`operator.install`), and the image helper and the image
arguments of the Operator (`--collector-image` and the like), which go through the kit's image helper and so honour
`global.imageRegistry`. A new Operator can bring a new language: switch it off by name in `operator.manager.extraArgs`,
or the chart tests fail.
